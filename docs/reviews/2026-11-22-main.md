## Summary
Spec 0001 is implemented faithfully: a strict Bun/TypeScript workspace, a boundary checker, a compiled-binary build for four targets, a process guard, and a careful native library home with self exec. `bun run check` passes (116 tests), CI and build workflows were green on all four targets at the last push, and the unit and e2e tests are good. Two majors remain. The boundary checker, which is the spec's headline guarantee, can be bypassed by inline `type` imports and `import("x")` type queries. The single `redact()` chokepoint misses the most common credential key names (`OPENAI_API_KEY`, `*_token`) and `_`-prefixed key shapes. The rest is minor hardening and doc drift.

## Major
### 🟠 Boundary check misses inline `type` imports and type-position `import()`, `scripts/check-boundaries.ts:112-139`
**Problem**: `scan()` relies on `Bun.Transpiler.scanImports` plus the regex `^\s*(?:import|export)\s+type\s...`. Bun drops type-only specifiers, and the regex only matches the `import type {...}` form. I ran the script on a fixture `agent` package containing `import { type CliRenderer } from "@opentui/core"` and `export type Q = import("openai").OpenAI`. The only violation reported was an unrelated one; both lines passed. `export type * from "x"` is caught, `import { type X }` and `typeof import("x")` are not.
**Why it matters**: The spec (Dependency rules) says the scan covers "type only imports" so a vendor SDK or UI type "can never leak into the core". The inline `type` modifier is the style `verbatimModuleSyntax` projects use all the time (the repo itself uses it in `export { type ... }`). tsc will not object because `node_modules` is hoisted, so nothing else catches it. The checker's test file has no case for it, so the gap is unguarded.
**Suggested fix**: Extend the type-only scan to cover `import { type A, ... } from`, `import type X = require()` and `import("x")` in type positions (a second regex, or parse with the TypeScript compiler API, which is already a dev dependency). Add test cases for each form to `scripts/check-boundaries.test.ts`.

### 🟠 `redact()` misses common credential key names and prefixed token shapes, `packages/env/src/redact.ts:15-16,19-27`
**Problem**: `SENSITIVE_KEY` is anchored (`^...$`), so only exact names match. Verified by running it: `{ OPENAI_API_KEY, github_token, "x-goog-api-key" }` and a nested `env: { ANTHROPIC_API_KEY }` all come back unredacted, while `apiKey` is redacted. The token patterns start with `\b`, and `_` is a word character, so `OPENAI_sk-abc...` or `key_sk-...` is not matched. `Map` values are silently dropped to `{}`, and a `Uint8Array` is expanded into an index-keyed object.
**Why it matters**: The spec makes `redact()` the one chokepoint for the logger, session writer, headless JSON and error formatting (#18, #24, #26). Env-style names (`*_API_KEY`, `*_TOKEN`, `*_SECRET`) are the most likely shape for a secret inside a logged or serialized object (a config dump, a tool input, a child env). The current tests only cover the exact-name list, so a regression to the more common forms would not be noticed.
**Suggested fix**: Match credential names by suffix or token, for example `(^|[-_.])(api[-_]?key|token|secret|password|passwd|credential)s?$` with care for count fields (`max_tokens`, `input_tokens`), and add a test for those. Replace `\b` with a lookbehind that treats `_` as a boundary for the token patterns. Handle `Map`/`Set` explicitly and pass typed arrays through unchanged.

## Minor
### 🟡 `--duration` usage error exits 2 with no message, `packages/cli/src/program.ts:172-181`
**Problem**: `parseDuration` throws a `CommanderError` with code `pk.usage`. Commander only prints for `InvalidArgumentError`, so the error reaches `main`'s catch (line 149), which returns `EXIT.usage` and prints nothing. Verified: `pk __tui-smoke --duration abc` exits 2 silently. The test at `program.test.ts:62` asserts only the exit code, so it passes anyway.
**Why it matters**: A usage error with no explanation. The same parser pattern will be copied for real flags.
**Suggested fix**: Throw commander's `InvalidArgumentError` (commander prints it and exits via `exitOverride`), and make the test also assert on `c.err()`.

### 🟡 `appendJsonl`, `atomicWriteFile` and the logger create folders and files with umask defaults, `packages/env/src/files.ts:22,74-75`, `packages/env/src/logger.ts:102`
**Problem**: `appendJsonl` has no `mode` option and `mkdir({ recursive: true })` passes no mode, so session, history and cost files come out 0644 inside 0755 folders. `atomicWriteFile` also does not keep an existing file's mode on replace. Only the log file is 0600.
**Why it matters**: Sessions and history contain prompts and file contents. Also, if the logger or a settings write creates `~/.pk` (macOS: cache and state are the same folder) before the native home check, a umask of 002 gives 0775 and the "can be changed by other users" check then permanently blocks interactive `pk`.
**Suggested fix**: Create pk-owned folders with 0700 and the record files with 0600 by default (a `mode` option on `appendJsonl`), and preserve the target's mode on atomic replace.

### 🟡 Native folder cleanup does not match its stated guarantee, `packages/cli/src/native-home.ts:360-388`
**Problem**: Cleanup removes entries whose mtime is over 7 days old, but a folder's mtime changes only when files are added to it, not when its library is used. A pk version used every day still gets removed 7 days after it first started, as soon as another version runs cleanup. The spec says a different version "starting at the same moment is never broken".
**Why it matters**: The folder is recreated on the next start (self healing), but a start that races a cleanup can hit a missing library and show the misleading "noexec mount" message.
**Suggested fix**: Touch (`utimes`) the target folder on each successful start so mtime means last used, and keep the 7 day rule.

### 🟡 `paths()` calls `homedir()` even when `PK_HOME` is set, `packages/env/src/paths.ts:33`, `packages/cli/src/program.ts:41-46`
**Problem**: `home` is evaluated eagerly. `resolveCacheDir` guards against a throwing `homedir()`, but `getLogger` calls `paths()` directly. In a container with no `HOME` and no passwd entry, `PK_HOME` set, the native home step succeeds and then the logger setup throws.
**Suggested fix**: Evaluate `homedir()` lazily, only when `PK_HOME` is unset.

### 🟡 Smoke screen leaks the renderer if `render()` fails, `packages/tui/src/smoke.tsx:79-100`
**Problem**: `createCliRenderer` has already taken the terminal when `render()` runs. If `render()` rejects, nothing destroys the renderer, and the guard has no screen to restore (the promise rejects).
**Suggested fix**: Wrap the `render` call, call `renderer.destroy()` on failure, then rethrow.

### 🟡 Logger rotation race between pk processes disables logging, `packages/env/src/logger.ts:68-76,109-111`
**Problem**: The spec expects concurrent pk processes. Each process rotates on its own cached size, and `existsSync` then `renameSync` is racy. A rename `ENOENT` falls into the catch and sets `disabled = true` for the life of that process, silently.
**Suggested fix**: Ignore `ENOENT` per rename inside `rotate`, and re-stat before rotating.

### 🟡 Boundary check is weaker than the spec in small ways, `scripts/check-boundaries.ts:183,201-209`
**Problem**: (a) The spec says declared dependencies "must equal" the table, but the script only rejects extras, so a declared and unused dependency passes. (b) The "reaches outside its package" test is `/^(\.\.\/){2,}/`, which wrongly flags a valid in-package import such as `../../x.ts` from `src/a/b/c.ts`, and is not computed against the package folder.
**Suggested fix**: Resolve the relative path and compare it to the package directory. Decide whether unused declared dependencies should fail.

### 🟡 Spec and docs drift after the green build, `docs/specs/0001-stack-architecture/index.md:133,148`
**Problem**: The build workflow is green on all four targets (Linux e2e included, binary 97 to 118 MB, `--version` startup 39 to 95 ms), but the spec still lists the Linux native library proof as an open follow up, says "The repo is not under git yet", and has no recorded outcome for the keep OpenTUI or switch to Ink decision, which the spec says to record as an update.
**Suggested fix**: Record the Linux outcome and sizes, close that follow up, state the OpenTUI decision, and drop the stale "not under git" line.

## Strengths
- The native library home is carefully built: fully injectable fs and execve, path checks that never follow links, loop guard that does not trust the marker alone, and a one line message per failure cause. It is backed by 30-odd unit tests plus real PTY e2e cases (1) to (7) that ran on all four CI targets.
- `process-guard` is a clean, injectable design with a restore timeout, raw escape fallback, signal and fatal paths, and `redact` on the fatal message; its tests are thorough (hang, reject, double signal, suspend failure).
- `check-boundaries.ts` has its own fixture based tests, and also handles shebangs, comments containing `Bun.`, and cycle detection. Build script, `define` injection, autoload off and per-target native id are all in line with the spec.
- Repo hygiene is good: strict tsconfig with per-package Node-only types, per-package typecheck, a test preload that isolates `PK_HOME`, a lockfile install in CI, and read-only workflow permissions.
