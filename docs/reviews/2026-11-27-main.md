## Summary
This is the terminal UI foundation (spec 0003). It adds a pure `reduceHud` reducer, a batched event store, a Solid shell with header, footer, rails, transcript, input and permission panel, a scripted demo session, the `__tui-demo` command, the TTY refusal, and `ui` settings (user only). The code is clean and follows the repo rules closely: Zod parse at the `details` boundary, `never` checks, no `any` and no `!`. Typecheck, lint, boundaries and the schema check all pass. The one headline issue is that `bun run check` (the gate) failed on my first run because of a wall-clock frame-time assertion, so the gate is flaky. The rest are minors.

## Major
### 🟠 Gate is flaky: wall-clock frame budget in the scroll test, `packages/tui/src/scroll-copy.test.tsx:114-115`
**Problem**: The "2,000 items" test asserts `p95 < 16ms` and `max < 33ms` on `performance.now()` deltas. On my first `bun run check` the max frame was 41.2 ms and the test failed. Three isolated runs and two further full `bun test` runs passed.
**Why it matters**: AGENTS.md says a feature is done only when `bun run check` passes. A timing assertion that depends on machine load will fail on CI, under lefthook, or whenever another process competes. That trains people to rerun and ignore failures. The first frame after cold JIT is the likely cause of the max outlier.
**Suggested fix**: Keep AC-25's intent but make the check deterministic. Either assert a structural proxy (the number of renders or cells written per scroll step), or discard warm-up frames and loosen `max` to something like 100 ms while keeping p95 as the stutter signal. Alternatively move the strict budget to `/check verify` or `test:e2e`, and leave only a generous smoke bound in the unit suite.

## Minor
### 🟡 Stream end or failure leaves the screen "working" forever, `packages/tui/src/hud/reduce.ts:399-402`
`ui_stream_end` and `ui_stream_failed` only add a notice or error. `turn.status` stays `running` and `submitting` stays `true`. The header keeps saying "working", the shared 100 ms spinner interval never stops (AC-19 intent), and tool lines still pending are never marked failed. Spec 0003 says the screen stays until Ctrl+C, so this is by design. A stream that dies mid-turn with the real session (#6) will still look alive. Treat both actions as an implicit turn end: set idle, clear `submitting` and `permissions`, and fail pending tools as `onTurnEnd` does. Add a reducer test.

### 🟡 `ERROR_HINTS[code]` reads inherited keys, `packages/tui/src/hud/reduce.ts:63`
`ERROR_HINTS` is a plain object indexed by a code that comes from model or provider data (`event.error.code`). A code such as `constructor` or `toString` returns a function from `Object.prototype`, and the error block renders `try: <function source>`. Look up with `Object.hasOwn` or use a `Map`. The same pattern applies to `ANSWERS[key.name.toLowerCase()]` in `packages/tui/src/shell.tsx:329`, which is safe only because key names are controlled.

### 🟡 `TuiExit.reason` can never be `"session_ended"`, `packages/tui/src/shell.tsx:461`
`startTui` always resolves `{ reason: "quit" }`, but `TuiExit` and spec 0003 declare `"quit" | "session_ended"`. The union member is dead and `cli` logs a reason that is always the same. Either produce it (the stream ended and the screen closed) or drop the member from the public type.

### 🟡 Scripted session timers outlive the screen, `packages/tui/src/demo/scripted-session.ts:101`, `packages/tui/src/hud/store.ts:78`
`sleep` schedules `clock.setTimeout` handles that are never cleared. `pumpEvents` only checks `isStopped` when the next event arrives and never calls the iterator's `return()`. With `pk __tui-demo --exit-after N` firing mid-turn, `main` returns, but `main.ts` only sets `process.exitCode`, so the process stays alive until the remaining scripted delays drain. This is hidden dev tooling, but the spec promises exit 0 on `--exit-after`. Cancel the run (reuse the `interrupt` path or a `dispose`) when the screen closes, or have `cli` exit explicitly after `closed`.

### 🟡 Synchronous `tmux` spawn on the render path, `packages/cli/src/program.ts:324-338`
`tmuxPassthrough` runs `spawnSync("tmux", ...)` with a 500 ms timeout from inside the selection handler, so a slow or hung tmux server blocks the UI thread for up to half a second per copy. The spec asks for a fresh read per copy, so the design is intended. Consider the async `spawn`, which `decideCopy` could await, or cache the value for a few seconds.

### 🟡 `sanitizeForScreen` leaves bidi and zero width controls, `packages/tui/src/text.ts:9`
C0, DEL and C1 are stripped, but U+202A to U+202E, U+2066 to U+2069 and U+200B to U+200F pass through. In the permission panel and tool targets, an RTL override can visually reorder a path or command so the thing you approve looks different from what runs. A C1 `\x9b` is stripped alone and leaves a visible `[2J`, which is harmless but untidy. Strip the bidi and zero width ranges, at least for permission and tool target text.

### 🟡 Tool name padding uses `.length`, `packages/tui/src/ui/transcript.tsx:252`
`l().name.padEnd(NAME_CELLS - 1)` pads by UTF-16 length, while every other width calculation uses `cellWidth`. A wide or combining tool name (names are model or MCP supplied) misaligns the target and right column and can overflow the line. Pad with `" ".repeat(NAME_CELLS - 1 - cellWidth(name))`.

### 🟡 No transcript or state bounding for long sessions, `packages/tui/src/hud/reduce.ts:68-93`
`addItem` copies the whole transcript for every appended item, and `addDelta` does `findLastIndex` plus `.with` (a full array copy) per delta. `tools` and `transcript` grow without bound, and `RightRail` runs `Object.values(tools).reverse()` on each state change. With the 33 ms batching this is fine at 2,000 items (the perf test shows it), but it is O(n) per delta for multi-hour sessions. Not urgent. Note it for #6 and consider trimming or chunking later.

### 🟡 Docs not updated for the new behavior, `packages/tui/AGENTS.md:5`
It still says "Today it holds only the smoke screen" and the cli AGENTS.md overview does not mention `__tui-demo` or the TTY refusal. Spec 0001 and this feature changed the package's real contents (`startTui`, `TuiSession`, theme, glyph and sanitize rules). That is a `/sync` task, but it should land with the change.

## Nits

- ⚪ `packages/tui/src/ui/hero.tsx:61`, `last.text += cell` mutates a local object in place. The repo says never mutate, so build runs with `reduce` or a fresh object.

## Strengths
- The reducer is genuinely pure and total, with an exhaustive `never` switch, subagent filtering, and `ToolDisplayDetails.safeParse` at the tool-result boundary. The 600 line reducer test covers the demo script end to end.
- Untrusted text is consistently routed through `sanitizeForScreen`, and `redact()` is applied exactly where the spec says (permission target and JSON, error code and message, notices). A source scan test enforces "no raw hex color or glyph outside theme.ts and glyphs.ts", and a design-doc test keeps the palette table and `docs/design.md` in step.
- The TTY refusal is a pure function that runs before the native library exec and before `@pk/tui` is imported. The `ui` setting is added to `USER_ONLY_SETTINGS` with a test, and the JSON schema is regenerated and checked.
- The 300 ms permission typing guard, the focus handling, and the one shared spinner interval with the idle-has-no-timers invariant are well thought out. Color-depth behavior is verified against the real binary's SGR output in e2e.
- `runScreen` in cli removes duplication between the smoke and demo commands and keeps the guard and native-home ordering intact.

## Test coverage
Strong: 400 tests, and 399 pass in the first full run (1 flaky failure, described above). The reducer, store batching, layout, rail fit, patch cutting, text and sanitize, theme and color modes, glyphs, copy decision, tmux parse, terminal refusal, settings trust, and the scripted session (every event parsed with `AgentEvent`) each have unit tests, and shell and transcript behavior has in-memory render tests with snapshots. Gaps: no reducer test for stream end during a running turn (see the Minor above), no test for an `ERROR_HINTS` prototype key, no unit test for `runScreen`'s PkError and native-load failure branches in `program.ts`, and nothing covers `--exit-after` actually ending the process.
